## What is this?

An experiment using [MyBatis](https://mybatis.org/) to implement the catalog queries. As you'd expect if you've been following along, the queries are artisanal hand-woven SQL but admittedly a lot of the configuration was generated by the bot.

In this _milieu_ objects are hierarchical (digital objects contain filesets) so the object table (`possible_objects`) sets up a simple parent/child structure. The mapper queries for objects lazily load children (and object files).

```java
@Result(property = "childObjects", column = "id",
        many = @Many(select = "findChildrenByParentId", fetchType = FetchType.LAZY)),

@Result(property = "objectFiles", column = "id",
        many = @Many(select = "org.example.aggrevateddata.ObjectFileMapper.findByPossibleObjectsKey", fetchType = FetchType.LAZY))
```

**Why are these _possible_ objects?** Because we don't like calling them _intellectual objects_ and no better word has emerged. 

## How to run this

```bash
# start up postgresql
docker compose up

# run the application
./gradlew bootRun
```

Then open http://localhost:8080/console/objects/ to view the _cough_ catalog. There's a `data.sql` file that's automatically loaded on startup[1].

Each object is linked to a detail view which lists its properties, its files, and its child objects (e.g. the monograph lists its filesets). If the version is greater than `1` it is linked to a page to list all versions. _Ta-da_

[1] shouldn't you need to have `spring.sql.init.data-locations=classpath:data.sql` defined? Doesn't seem like it.

## What else?

`ImportDataController` has a route to import data from files in `tmp`, and a route to randomly generate versions from random sampling of the existing data. _Are controllers the best approach?_ Probably not! But command line actions seem tricky to run while the server is running. _Whomp whomp._

## What is the catalog?

Where we end with philosophy.

The schema is designed to support our original function --- **find an object by its (alternate) identifierr** -- _and_ support generating what I'd call **firehose reports**. These reports are perhaps _not_ as useful for content managers who would be using the console for more targeted purposes (this collection, this set of objects, etc.)

Examples of these reports from our peers are available in the [Repo Admin UI Research](https://miro.com/app/board/uXjVILJ9BRQ=/) board.

Noah has brought up the blurry edge between the catalog and the analytical queries supported by truer OLAP systems and that's probably true! Before the console does anything more than what's illustrated in the above board we should investigate this tangent.

**What does it mean to find an object by way of the catalog?** That's still a question! I suspect it's not related to the cached data: probably more of this process: 

- find an object by way of an identifier
- load the inventory from the preservation storage

**Why else make a cache of object files?** Beyond the firehose reporting _possibly_ to drive an Image API, but that's a _huge_ TBD (are service files part of the catalog? does the Image API ever interact with depot/preservation?)

As always, we end with more questions.
